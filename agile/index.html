Project overview

Purpose of this portfolio

This page records Agile planning artefacts and learning reflections for the Sewage Repair Services project. The proposed service combines a digital reporting platform, routine sewer inspections and a repair team. Residents can report blocked drains, burst pipes and sewage overflows, while staff can manage reports and update repair progress.

Agile Team Charter

Purpose and shared goal

Our project goal is to design a practical digital service that makes it easier for Khayelitsha community members to report sanitation problems and follow the progress of repairs.

Working agreements

  • Break project work into small, understandable tasks.
  • Keep task progress visible and communicate blockers early.
  • Discuss changes before they affect shared work.
  • Review work and test functionality before treating a task as complete.
  • Respect team members and share relevant project information.

Roles and communication

Work is organised around the needs of residents, administrators and repair personnel. Team responsibilities and communication arrangements should be recorded using the group's agreed roles and channels.

Reflection

Creating a team charter helps make expectations visible instead of assuming everyone understands how the team should work. I learned that clear communication, task ownership and early discussion of blockers are important in a shared software project. I would improve the charter by recording specific owners, response expectations and an agreed process for resolving disagreements.

User Stories and Tasks

User stories describe functionality from the perspective of the people who will use the service.

IDUser storyExample tasksPriority
US01As a resident, I want to submit a sewage problem report so that the responsible team can investigate it.Create report form; validate required fields; save report and location.High
US02As a resident, I want to view the status of my report so that I know whether it is being handled.Generate report reference; display status; show progress stages.High
US03As an administrator, I want to view incoming reports so that I can coordinate responses.Build report list; display report details; filter by status.High
US04As an administrator, I want to assign a repair team so that a reported problem has someone responsible for it.Display available teams; assign team; save assignment.Medium
US05As a repair worker, I want to update a job status so that progress can be communicated.Provide status controls; save status change; display updated status.Medium

Reflection

Writing user stories helped me think about the system from the user's point of view rather than starting with technical tasks. I learned that a useful story explains both the requested function and the reason it matters. Breaking stories into smaller tasks also makes work easier to estimate, assign and review. I would strengthen these stories by adding measurable acceptance criteria and validating them with intended users.

Product Backlog

The product backlog is a prioritised list of work that may be needed to deliver the service. Priorities below are proposed and can change as requirements are clarified.

IDBacklog itemPriorityAcceptance outcome
PB01Submit a sewage issue reportHighA resident can submit an issue with its type, description and location.
PB02View and track a submitted reportHighA report can be identified and its current status viewed.
PB03Administrator report dashboardHighStaff can view and review submitted reports.
PB04Assign repair personnelMediumAn authorised staff member can associate a team with a report.
PB05Update repair statusMediumProgress can be updated and shown to the relevant user.
PB06Record inspection activityMediumInspection observations can be recorded for maintenance follow-up.

Reflection

The product backlog gives the project one ordered view of the work still needed. I learned that prioritisation should be based on user value and dependencies, not simply on which feature is easiest to build. The core reporting and tracking functions should come before enhancements. The backlog should remain flexible and be refined when feedback, technical constraints or new information changes what is most valuable.

Reflection

A sprint backlog turns selected product goals into work that can be acted on during a short development cycle. I learned that a clear sprint goal helps the team focus and that tasks need to be small enough to track. Comparing planned work with completed work can reveal blockers and unrealistic estimates. I would improve sprint planning by checking task dependencies and capacity before committing to the sprint.
